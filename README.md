# AntiSpamBee

AntiSpamBee — Telegram-бот модерации рекламы и спама. Он анализирует сообщения,
bio, личный канал пользователя и публичные реакции, сохраняет объяснимые сигналы
и выполняет действия через надёжную очередь.

## Что уже работает

- защищённый Telegram webhook с ограничением размера и secret token;
- NATS JetStream с durable consumer и дедупликацией по Telegram `update_id`;
- PostgreSQL-события, detector signals, решения, действия и audit log;
- реклама работы, adult/порно, VPN, казино, крипты, займов и обычные промо;
- скрытые `text_link`, URL и базовая нормализация обфускации;
- разделённые и смешанные кириллическо-латинские ключевые слова, а также `t[.]me`;
- сообщения от имени канала, `channel_post` и `edited_channel_post`;
- локальный OCR изображений через Tesseract `rus+eng` под флагом `OCR_ENABLED`;
- анализ bio, username, личного канала и его последних публикаций;
- проверка профиля пользователя, поставившего реакцию;
- flood, повторяющиеся сообщения и история предыдущих нарушений;
- OpenRouter `~typesafe/jev-latest`: уверенный сигнал удаляет рекламу, а бан требует независимого подтверждения;
- allowlist, пользовательские жалобы и Telegram-команды модераторов;
- идемпотентный Action Worker с lease, retry, `retry_after`, reconciliation и DLQ.
- privacy-safe диагностика входа: тип update, длины текста/OCR, наличие ссылки,
  виды медиа и SHA-256 отпечаток без сохранения исходной переписки.

## Политика действий

```text
risk < 0.90       → ALLOW
risk 0.90–0.999…  → DELETE_MESSAGE или DELETE_REACTION
risk = 1.00       → DELETE_MESSAGE/DELETE_REACTION + BAN_USER
```

Автоматическое действие дополнительно требует confidence `>= 0.90`, evidence
coverage `>= 0.50`, разрешённую policy и непривилегированного пользователя.
Администраторы, владелец и allowlist никогда не банятся автоматически. Ошибка
проверки статуса пользователя приводит к повторной обработке события.
Временная ошибка профиля (`429`, `5xx`, сетевой timeout) также повторяется,
если сообщение ещё не распознано как реклама; уже подтверждённая текстовая
реклама удаляется без ожидания профильного API.

Jev включается только при наличии `OPENROUTER_API_KEY`. Уверенный модельный
сигнал ограничен delete-only риском `0.97`; до `1.00` он повышается только при
независимом подтверждении детерминированным фильтром.

OCR включается через `OCR_ENABLED=true`. По умолчанию загрузка Telegram-файла
ограничена 8 МБ, распознавание — 12 секундами, язык — `rus+eng`. Production
образ moderation worker уже содержит Tesseract и оба языковых набора. При
ошибке OCR событие повторяется и не превращается в молчаливый `ALLOW`.

Поток выполнения:

```text
Telegram → Gateway → JetStream → Detectors → Decision Engine
                                      ↓
PostgreSQL ← signals + decision + queued action
                                      ↓
                            Action Worker → Telegram
```

## Telegram-интерфейс

- `/start`, `/help` — подробный справочник и кнопка «Добавить в группу»;
- `/report` — пожаловаться, отправив команду ответом на сообщение;
- `/status` — текущий режим защиты;
- `/history CHAT_ID` — последние 5 сохранённых решений в ЛС (ID группы указан в `/status`);
- `/protection observe|soft|standard|strict` — изменить режим;
- `/allow`, `/unallow` — управление allowlist ответом на сообщение;
- `/warn`, `/mute`, `/ban` — действие модератора ответом на сообщение;
- `/unban USER_ID` — снять блокировку по Telegram ID.

Кнопка добавления открывает системный выбор группы Telegram и запрашивает только
права удаления сообщений и ограничения участников. После подтверждённого
успешного бана бот публикует в защищаемой группе уведомление с Telegram ID
заблокированного пользователя.

`cmd/setup-webhook` одновременно регистрирует webhook и заполняет нативное меню
команд Telegram, которое открывается кнопкой `/`.

Административные команды проверяют статус вызывающего пользователя через
`getChatMember`. `/ban` и `/mute` попадают в Action Worker, а не вызывают
разрушительный Telegram API напрямую.

Режимы: `OBSERVE` и `SOFT` оставляют решение модератору, `STANDARD` разрешает
удаление явной рекламы, `STRICT` использует те же безопасные границы удаления.
Автобан временно приостановлен в политике `message-evidence-v2`, независимо от
старого флага `autoban_enabled`. Ручной `/ban` администратора остаётся доступным.
Оценка профиля, история машинных срабатываний и модель без текста текущего
сообщения не разрешают автоматическое удаление. Сигналы не складываются до «100%».
JEV оценивает только текст/подпись/OCR сообщения, без профиля автора.

После автоматического удаления бот отправляет в личные сообщения администратору,
добавившему бота в группу, `@username` автора (либо ID при отсутствии username),
текст удаления и причину. Администратор должен предварительно открыть личный чат
с ботом и отправить `/start`: иначе Telegram запрещает боту написать первым. Для
групп, в которые бот был добавлен до включения этой функции, администратор может
один раз выполнить `/protection strict` в группе — это назначит его получателем.

Для новых решений REVIEW и действий журнал сохраняет исходные текст/подпись,
OCR, контекст профиля, сигналы, версию политики и доступные сведения о версии модели
на 30 дней. Длинные поля ограничены, факт сокращения отмечается в снимке.
Старые удалённые тексты не восстанавливаются. `/history` требует и привязку,
и актуальные права администратора; личный ID не извлекается из анонимного сообщения.

Уведомление об успешном удалении сохраняется транзакционно в отдельную очередь.
Временные ошибки повторяются до 5 попыток с учётом Telegram retry_after;
окончательный сбой виден в `moderation_notification_outbox`. Перед отправкой
перепроверяются привязка и права получателя. Повтор доставки не повторяет удаление.
После неоднозначного сетевого сбоя уведомление может прийти повторно:
Telegram sendMessage не предоставляет ключ идемпотентности в этом клиенте.
Просроченные снимки/уведомления очищаются action-worker каждую минуту пакетами
по 100 строк; при остановленном worker просроченный журнал всё равно недоступен.

Для удаления сообщений и реакций боту необходимо право
`can_delete_messages`, для ban/mute — `can_restrict_members`. Webhook должен
включать `message_reaction`; setup-команда делает это автоматически.

## Локальный запуск

Требования: Go 1.23+, Docker и Docker Compose. Для локального запуска OCR без
Docker дополнительно нужен Tesseract с языками `rus` и `eng`.

```bash
docker compose up -d
cp .env.example .env
# Заполните Telegram-параметры. OPENROUTER_API_KEY можно оставить пустым.
set -a
. ./.env
set +a
```

Запустите три процесса:

```bash
go run ./cmd/gateway
go run ./cmd/moderation-worker
go run ./cmd/action-worker
```

После публикации HTTPS endpoint зарегистрируйте webhook:

```bash
go run ./cmd/setup-webhook
```

Health endpoints:

- gateway: `:8080/healthz`, `:8080/readyz`;
- action worker: `:8081/healthz`, `:8081/readyz`;
- moderation worker: `:8082/healthz`, `:8082/readyz`, `:8082/metrics`.

## Production Compose

Задайте настоящий `POSTGRES_PASSWORD` и секреты в `.env`, затем:

```bash
docker compose -f compose.prod.yml up -d --build
```

Сервис `migrate` применяет ещё не выполненные SQL-миграции до запуска workers.
Не храните `.env` в Git. Если API-ключ когда-либо публиковался в чате или Git,
его необходимо отозвать и создать новый.

## Проверка

```bash
go test -race ./...
go vet ./...
go build ./cmd/gateway
go build ./cmd/moderation-worker
go build ./cmd/action-worker
go build ./cmd/setup-webhook
```

CI поднимает PostgreSQL, применяет миграции, запускает integration tests, race
detector, vet и сборку всех команд.

## Ограничения текущего MVP

- реклама, существующая только внутри картинки или аватара, пока не проходит OCR;
- анонимную реакцию `actor_chat` нельзя связать с конкретным пользователем;
- Jev остаётся выключенным без нового безопасно переданного ключа и расширенного размеченного golden set;
- production backup/restore и внешний маршрут апелляции настраиваются отдельно.
